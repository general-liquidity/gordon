# Gordon v0.9 Architecture Roadmap

This document defines the v0.9 architecture plan for Gordon.

It is informed by a comparative study of the leaked `open-claude-code-main` codebase, but Gordon must remain a clean-room implementation. We should reuse architectural patterns and product lessons, not code.

## Executive Summary

Gordon already has strong domain depth in trading, risk, execution, audit, and broker/exchange integration. The main weakness is not product ambition. It is runtime shape.

Today, too much control flow is split across:

- `src/index.tsx`
- `src/app/App.tsx`
- `src/infra/agents/orchestrator.ts`
- `src/infra/agents/agents.ts`
- `src/infra/storage/session.ts`
- `src/gateway/runtime/gateway-runtime.ts`

That makes Gordon harder to:

- test headlessly
- expose via SDK/API/daemon consistently
- extend with richer permission models
- support long-running sessions cleanly
- add finance-native worker coordination

The v0.9 goal is to introduce a real runtime core without losing Gordon's trading-specific strengths.

## Current Diagnosis

### Strengths

- Strong domain-specific trading and financial execution logic
- Meaningful gateway/daemon foundations already exist in `src/gateway`
- Existing audit, scheduler, action log, autonomous mode, and reconciliation surfaces
- Rich tool surface for markets, execution, onchain, backtests, and playbooks
- Better finance depth than general-purpose agent CLIs

### Structural Problems

1. `src/app/App.tsx` is too large and too stateful.
   - Current size is roughly 4.8k lines.
   - It owns UI rendering, runtime mutation, session coordination, slash/runtime command handling, background status wiring, and product state.

2. `src/infra/agents/orchestrator.ts` is too large and too central.
   - Current size is roughly 3.2k lines.
   - It mixes streaming, prompt assembly, lifecycle, tool policy, tracing, repair, and agent loop control.

3. Gordon does not have a first-class session/query runtime abstraction.
   - The TUI and gateway both depend on orchestrator entrypoints.
   - There is no single reusable runtime owner for turn execution, session mutation, permission context, and transcript lifecycle.

4. Tool registration is broad but not formal enough.
   - `src/infra/agents/tools/index.ts` is a giant export surface.
   - Tools are not yet governed by one typed capability/risk/permission contract.

5. Session state is fragmented.
   - There is local session persistence in `src/infra/storage/session.ts`
   - thread management in `src/infra/agents/threadManager.ts`
   - UI state in `App.tsx`
   - daemon/gateway request state in `src/gateway`
   - audit/action history elsewhere

6. Permissioning is still too coarse for the product direction.
   - `SAFE` vs `ARMED` is useful, but not enough for a serious agentic finance platform.
   - Future Gordon needs explicit scopes and action classes.

7. MCP, routing, skills, plugins, and action rails are not yet one coherent capability system.

## Architecture Principles

1. Runtime-first, UI-second
   - The runtime owns execution.
   - The TUI renders state and dispatches actions.

2. Finance-grade permissioning
   - Every side effect must map to a capability scope and audit class.

3. Clean session ownership
   - One runtime object owns a session or thread lifecycle.

4. Deterministic control plane
   - Status, mode transitions, approvals, and background orchestration should not depend on model interpretation.

5. Domain depth over generic breadth
   - Gordon should become the best financial agent runtime, not a clone of a generic coding agent.

6. Clean-room implementation
   - We can adopt patterns visible in another product.
   - We must not port code or structure too literally.

### Ownership model

- `app`
  - TUI only
  - render state
  - dispatch user intent
  - no deep business state ownership

- `infra`
  - adapters and integrations
  - LLM provider wiring, MCP, storage, broker/exchange, observability

- `gateway`
  - daemon and external control plane over the runtime

## New Runtime Core

The most important new abstraction is `SessionRuntime`.

### `SessionRuntime`

Responsibilities:

- own one Gordon session/thread
- accept user input or command input
- maintain runtime state
- invoke the query loop
- expose stream events
- apply permission policy
- register audit events
- coordinate compaction and replay
- own worker/specialist handoffs

Proposed shape:

```text
src/runtime/session/
  SessionRuntime.ts
  SessionRuntimeFactory.ts
  SessionContext.ts
  SessionController.ts
```

### `QueryRuntime`

Responsibilities:

- run one turn
- prepare model/tool context
- invoke orchestrator or main agent loop
- normalize tool calls and tool results
- emit stream chunks
- update session state

Proposed shape:

```text
src/runtime/query/
  QueryRuntime.ts
  QueryLoop.ts
  QueryInput.ts
  QueryResult.ts
```

### `RuntimeStore`

Responsibilities:

- keep canonical runtime state independent of Ink
- allow TUI, daemon, scheduler, and tests to observe the same state model

Proposed shape:

```text
src/runtime/state/
  RuntimeStore.ts
  SessionState.ts
  BackgroundState.ts
  StreamState.ts
```

## Tool Architecture Upgrade

The tool system should move from "large export surface" to "formal capability registry".

### New tool contract

Each tool should declare:

- `id`
- `category`
- `riskClass`
- `permissionScope`
- `sideEffectLevel`
- `supportsStreaming`
- `supportsBackground`
- `requiresArmedMode`
- `auditEventType`
- `idempotencyBehavior`
- `inputSchema`
- `outputSchema`

### Proposed structure

```text
src/runtime/tools/
  ToolSpec.ts
  ToolRegistry.ts
  CapabilityRegistry.ts
  ToolInvoker.ts
  ToolPolicy.ts
```

### Permission scopes

At minimum:

- `market.read`
- `analysis.run`
- `portfolio.read`
- `papertrade.execute`
- `livetrade.execute`
- `transfer.execute`
- `wallet.write`
- `system.mode.write`
- `runtime.background.write`
- `plugin.install`
- `mcp.connect`

This does not replace `SAFE` and `ARMED`. It refines them.

## Permission Model Upgrade

Current model:

- coarse mode gating
- selective tool guards

Target model:

- explicit capability scopes
- approval classes
- deterministic evaluation path
- audit trail for every approval decision

### Approval classes

- `none`
- `session`
- `per_action`
- `per_tool`
- `always_require_human`

### Why this matters

A finance agent cannot stop at "armed vs not armed". It needs approval semantics matching:

- analysis
- simulated execution
- live execution
- fund movement
- policy mutation
- plugin or MCP trust changes

## Session and Transcript Model

Gordon needs a first-class session system more like a runtime log than a loose combination of thread storage and UI history.

### New session model

Each session should own:

- session identity
- active thread
- turn history
- usage and cost
- permission context
- background tasks
- worker graph
- compaction checkpoints
- audit metadata

### Proposed structure

```text
src/runtime/transcript/
  TranscriptStore.ts
  CompactionManager.ts
  ReplayManager.ts
  TranscriptProjector.ts
```

### Immediate goal

Make replay, compaction, resume, and daemon-driven sessions use the same transcript model.

## Agent Runtime Refactor

`src/infra/agents/orchestrator.ts` should stop being the place where every concern accumulates.

### Split target

- `orchestrator.ts`
  - thin top-level coordination only
- `prompt assembly`
  - separate
- `stream lifecycle`
  - separate
- `tool policy and evaluation`
  - separate
- `repair/validation`
  - separate
- `usage/cost tracking`
  - separate
- `worker handoffs`
  - separate

### Proposed structure

```text
src/infra/agents/
  orchestrator/
    AgentOrchestrator.ts
    PromptAssembler.ts
    StreamCoordinator.ts
    ToolCallCoordinator.ts
    TranscriptRepair.ts
    HandoffCoordinator.ts

```

`src/infra/agents/agents.ts` should also shrink into an agent factory plus registry rather than remaining a large initialization hub.

## UI Refactor Plan

`src/app/App.tsx` should become a screen shell, not the product runtime.

### Extract from `App.tsx`

- session control
- mode transitions
- background task polling
- command execution
- status aggregation
- streaming orchestration
- runtime mutation

### Keep in `App.tsx`

- view selection
- keyboard wiring
- overlay orchestration
- presentational state binding

### Proposed app structure

```text

  state/
    AppStore.ts

  presenters/

    TaskTreePresenter.ts
    ChatPresenter.ts

```

## Plugin, Skill, and MCP Unification

Gordon currently has parts of this story, but not one clean contract.

Target system:

- one capability registry
- one trust source model
- one installation state model
- one policy evaluation path

### Distinction we should keep

- `skills`
  - prompt/workflow augmentation
- `MCP servers`
  - external tools/resources
- `plugins`
  - Gordon-native packaged integrations

### What should be unified

- manifest shape
- capability declarations
- trust level
- install/enable/disable lifecycle
- permission requirements
- routing target
- audit metadata

## Finance-Native Worker Architecture

We should not copy generic coding-agent swarms directly.

We should build specialist roles that map to finance:

- `Analyst`
- `Planner`
- `Risk`
- `Executor`
- `Monitor`
- `Critic`
- `Auditor`

### Worker model

- every worker receives an explicit scope
- every worker writes structured handoff artifacts
- no free-form hidden delegation
- scratchpad should be typed, auditable, and persistent

### Proposed structure

```text
src/runtime/workers/
  WorkerSpec.ts
  WorkerRegistry.ts
  HandoffArtifact.ts
  ScratchpadStore.ts
  SpecialistPolicies.ts
```

## v0.9 Delivery Phases

### Phase 1: Runtime extraction

Goal:

- introduce `SessionRuntime`
- route TUI and gateway through it

Concrete work:

- create `src/runtime/session/*`
- create `src/runtime/query/*`
- wrap current orchestrator calls behind runtime methods
- move session/thread ownership out of `App.tsx`

Acceptance criteria:

- TUI chat and daemon chat both use the same runtime API
- no direct orchestrator invocation from `App.tsx`

### Phase 2: Runtime store

Goal:

- replace ad hoc UI state ownership with a canonical runtime store

Concrete work:

- add `RuntimeStore`
- bind `App.tsx` to store selectors
- move background task state and stream state into runtime

Acceptance criteria:

- state mutations happen through store actions, not ad hoc React chains

### Phase 3: Tool and permission registry

Goal:

- formalize tool metadata and approval policy

Concrete work:

- add `ToolSpec`
- add `CapabilityRegistry`
- classify existing tools by risk class and permission scope
- route `SAFE` / `ARMED` checks through capability policy

Acceptance criteria:

- every mutating tool has a declared scope
- approval decisions are auditable and deterministic

### Phase 4: Transcript and compaction

Goal:

- make long-lived sessions reliable

Concrete work:

- create transcript store and replay manager
- unify session restore and daemon/session replay
- centralize compaction boundaries

Acceptance criteria:

- resume, compaction, and background modes use one transcript model

### Phase 5: Agent runtime split

Goal:

- shrink `orchestrator.ts` and `agents.ts`

Concrete work:

- split prompt assembly, stream coordination, usage tracking, repair, and handoffs into dedicated modules
- reduce orchestrator to composition layer

Acceptance criteria:

- `orchestrator.ts` becomes coordination code, not a god file

### Phase 6: Worker kernel

Goal:

- introduce finance-native specialist delegation

Concrete work:

- worker registry
- structured handoff artifacts
- persistent scratchpad
- explicit planner/risk/executor/monitor flow

Acceptance criteria:

- delegation is typed, inspectable, and recoverable

## File-by-File Extraction Targets

### Highest priority

- `src/app/App.tsx`
  - extract runtime ownership
  - keep view composition only

- `src/infra/agents/orchestrator.ts`
  - split into orchestrator modules

- `src/infra/agents/agents.ts`
  - convert into agent factory + registry + agent config

- `src/infra/storage/session.ts`
  - move from "session file helper" toward a richer session store owned by runtime

- `src/gateway/runtime/gateway-runtime.ts`
  - make it depend on `SessionRuntime`, not orchestrator internals

### Secondary priority

- `src/infra/agents/tools/index.ts`
  - evolve into registration layer over typed specs

- `src/infra/mcp/*`
  - unify trust/capability metadata

- `src/app/commands/*`
  - route through runtime service layer instead of app-local state mutation

## Non-Goals for v0.9

- Full package split / monorepo split
- Browser automation or voice expansion
- Broad generic plugin marketplace complexity
- Rebuilding the whole TUI from scratch
- Replacing Gordon's domain-specific finance logic with generic agent abstractions

## Immediate Next Tasks

1. Introduce `src/runtime/session/SessionRuntime.ts`
2. Introduce `src/runtime/state/RuntimeStore.ts`
3. Create a thin adapter in `App.tsx` to use `SessionRuntime`
4. Create a thin adapter in `gateway-runtime.ts` to use `SessionRuntime`
5. Add `ToolSpec` and classify the highest-risk tools first
6. Split `orchestrator.ts` into dedicated coordinator modules

## Success Criteria

v0.9 is successful if:

- Gordon has one real runtime core
- the TUI is no longer the source of truth
- tool permissions are capability-based and auditable
- daemon and TUI share the same execution path
- specialist delegation becomes structured and finance-native
- the codebase becomes easier to test, extend, and reason about
